On-device AI research assistant.

Researchers add their own journal PDFs and ask questions about them. The app answers with citations to the exact passages, and everything runs on the phone, so no paper is ever uploaded.

The problem

Researchers want quick, trustworthy answers from their own papers, but many can't or won't send unpublished or licensed papers to a cloud AI service. The answers also have to be grounded: a research tool that invents a number is worse than no tool. And it has to work on the mid-range Android phones most of its users own, not just flagships.

How it works

  1. ImportPDFs come in through the document picker and stay on the device.
  2. Extract and chunkText is extracted natively, split into chunks and tagged by section, such as methods or results.
  3. Embed and storeA small on-device embedding model turns each chunk into a vector, stored in SQLite with the sqlite-vec extension.
  4. RetrieveVector search is combined with term scoring and section routing, so a question about methods favours the methods section.
  5. AnswerA 0.6B-parameter language model running through ExecuTorch writes an answer from the retrieved evidence only, with APA-style citations.

Hard parts and decisions

  • Getting models onto the phoneModel files download in the background, a stuck download resumes instead of starting over, and the app restarts only the model that isn't ready.
  • Speed on mid-range phonesI reworked the answer setup and prompt so answers start much sooner on mid-range Android phones.
  • Measuring accuracy honestlyEvery release runs a fixed test on fresh papers, with pass marks written down before the run and every answer scored by hand.
  • Catching invented numbersI tested off-the-shelf fact-checking models against hand-scored answers. They didn't separate right from wrong answers well enough, so I chose cheap text rules that flag numbers taken from the wrong place in the evidence.
  • Memory before speedI worked out peak memory against the model's context length before testing on low-RAM phones, because a crash there matters more than a faster answer.

The problem

Writing a question bank by hand is slow, and exam material shouldn't leave the organisation. The same app also has to run the exam operation itself: centres, clusters, papers, students and who is allowed to do what.

How it works

  1. UploadStudy material comes in as files, and text is extracted from PDFs on the device.
  2. IndexOne file at a time is read, split into chunks and embedded with an on-device embedding model, with progress shown per file.
  3. GenerateA language model running through ExecuTorch drafts questions from the indexed material into the question bank.
  4. AssembleQuestions are organised by subject into papers, and students can be added in bulk.

My part

What I builtI wrote the mobile app. The product as a whole was a team effort, and I worked on it with the team on the product side too.

Engineering highlights

  • Long AI jobs that survive the backgroundA foreground service, added through a custom Expo config plugin, keeps indexing and generation running when the user leaves the app.
  • One pipeline, two modelsThe embedding and generation models share one pipeline that tracks when each is ready and retries only what failed.
  • Roles and permissionsScreens and forms to manage roles, permissions and users, so each admin sees only what they're allowed to.
  • Typed data end to endTanStack Query and Axios for the API, Zod to validate responses, Drizzle ORM over SQLite for local data, and Secure Store for credentials.

Authorised officials record exam scores on their phones in places where the connection can't be trusted, and every entry has to reach the server intact.

The problem

Scores are official records, entered in large volumes, often with no signal. Losing an entry or saving half a batch is not acceptable, and officials need to see progress across many schools.

How it works

  1. DownloadEach official's assigned work is fetched while the phone is online.
  2. EnterFast numeric entry, with a way to mark absent candidates, works with or without a connection.
  3. StoreEvery entry is saved to SQLite on the device the moment it is made.
  4. SyncCompleted scores are submitted when connectivity returns, with progress shown for each school.

My part

What I builtI built the offline-first score entry with records stored on the device, then added synchronization to submit captured scores when connectivity returns. I also built the dashboard and analytics features for monitoring exam activity.

Design decisions

  • Save first, sync laterWriting locally on every keystroke-level change means a crash or dead battery loses nothing.
  • Sync completed work onlySubmitting finished batches keeps the server from receiving half-entered results.
  • Role-aware sign-inOfficials who sign in are taken straight to an admin view for managing examiners and tracking progress.

Field data collection.

Enumerators travel area by area to map schools and capture detailed records, mostly where there is little or no connection.

  • Expo

The problem

Each enumerator builds up a large local dataset over days in the field. The app has to stay fast as that data grows, keep every field valid, and reconcile cleanly with the server when the team gets back online.

How it works

  1. CaptureStructured forms with field-level validation, organised by local area, with the device's location.
  2. Store locallyRecords live in a local database built on SQLite and Drizzle ORM.
  3. ReconcileSync reconciles field records with the backend once connectivity returns.

My part

What I builtI designed the local-first data architecture so enumerators can work with school records offline, then built the synchronization that reconciles field records with backend data. I also investigated performance problems with large local datasets, in both list rendering and database queries.

Design decisions

  • A typed local schemaDrizzle ORM keeps queries type-checked against the SQLite schema, so form changes don't silently break stored data.
  • Profile before optimisingSlowdowns were traced to specific list renders and queries before anything was changed.

Exam candidate registration.

Schools register their candidates for state exams from a phone: personal details, a passport photo, subjects and continuous assessment scores.

  • React Native
  • Expo
  • TypeScript
  • Camera
  • On-device AI photo check
  • REST APIs
2022--

The problem

Registration data feeds official exams, so it has to be complete and the photos usable. Some candidates were being registered with random or placeholder pictures instead of a real passport photo, which opened the door to fraud and false registrations. School staff also often work on weak connections and handle two different exams with different rules.

How it works

  1. DetailsOne form per candidate across three steps: personal details, subjects, then scores.
  2. PhotoA passport photo from the camera or gallery goes through an AI check that runs on the phone, not in the cloud. It confirms the picture shows a real human face, clear and front facing, and rejects random and placeholder pictures before the user can continue.
  3. Subjects and scoresCompulsory subjects are added automatically, electives are chosen, and CA 1, CA 2 and CA 3 are entered per subject.
  4. Save safelyIf the connection drops while saving, changes are kept and sent once the phone is back online.

Engineering highlights

  • An on-device AI check on every passport photoRejecting any picture that isn't a real person's face stops registrations made with random or placeholder images, which cuts fraud and false entries. Running it on the phone means it works on weak connections and photos are checked before they are uploaded.
  • Validation at captureRejecting a bad photo during registration is far cheaper than chasing it after submission.
  • Exam-aware themingThe app's colours change with the selected exam, so staff always know which one they are working in.
  • Work that needs attentionThe home screen counts missing assessment entries so nothing is left incomplete.

responsive-rn: one layout system for every screen size.

A small TypeScript library that gives React Native and Expo apps breakpoints, design tokens, fluid values and layout components, so screens adapt from small phones to tablets without layout maths in every component.

The idea

Across my apps I kept writing the same code: read the window width, pick a padding, guess a font size, work out how many cards fit in a row. Every screen did it slightly differently, so spacing drifted and tablets looked like stretched phones. responsive-rn moves those decisions into one place. An app sets its breakpoints and design tokens once, and every component asks the library for the right value instead of calculating its own.

smallphonetabletlarge
0320600840+ pt

How it works

  1. One providerA ResponsiveProvider at the root reads the screen size and merges the app's config with sensible defaults, so an app only overrides what it needs.
  2. BreakpointsDefault thresholds follow Material Design 3 layout breakpoints, and every one is configurable.
  3. Tokens by tierSpacing, type sizes, corner radii and icon sizes are defined per breakpoint, and useLayout returns the right set for the current screen.
  4. Values that cascadeWith useResponsiveValue, a value only needs defining where it changes. Missing tiers fall back to the nearest smaller one.
  5. Fluid valuesuseFluidValue scales smoothly between two sizes as the width changes, like CSS clamp, for things that shouldn't jump at a breakpoint.
  6. Layout componentsContainer, Row and Grid components, plus Show and Hide for rendering by breakpoint and a debug overlay for development.

The grid measures its own space

Most grids choose columns from the screen width. That breaks inside split views, side panels and cards, where the space a grid actually gets is much smaller than the screen. ResponsiveGrid measures the width of its own container and works out how many columns fit:

columns = floor((width + gap) / (minItemWidth + gap))

The result is then clamped between a minimum and maximum column count. When a screen needs an exact layout, a fixed column count per breakpoint overrides the calculation. Items can be fixed, responsive or aspect-ratio sized, and a short last row can expand to fill the space.

Design decisions

  • Defaults grounded in platform guidanceBreakpoints follow Material Design 3, spacing follows an 8-point grid, buttons and inputs never go below a 48-point touch target, and body text never drops below accessible sizes.
  • Pure functions, tested on their ownBreakpoint flags, layout tokens, cascading values, fluid values, grid columns and row stacking are pure functions, covered by 8 Jest test files without rendering a component.
  • Fewer re-rendersThe provider compares the merged config deeply and only gives components a new value when something actually changed.
  • Zero runtime dependenciesReact and React Native are peer dependencies only, so installing the library adds nothing else to an app.
  • Configurable everywhereConfig is deep-merged with the defaults, and props passed directly to the provider take precedence, so a team can adopt it gradually.

Where it's used

I use it across 10 of my own app projects, including the on-device AI research assistant and the exam admin app on this page. It has had 20 releases and more than 2,900 downloads on npm.
